# Deploying the 2026-08-31 changes to gpu6

Fourteen commits, `6f440f7..HEAD`. **Code only** — `models/` is gitignored, so a
pull cannot touch the server's encrypted weights, and the recognizer is
unchanged (IR-101, the model already deployed there). Nothing needs re-encrypting
and no model is transferred.

The compiled core (`app/core/*.so`) IS tracked and does travel: the server has no
sources for it. It is cp310 ABI-locked, which is what `~/faceid/miniconda`
(Python 3.10.13) exists for.

The ReID model travels with the code. `models/` is ignored wholesale, but
`reid_resnet101_ibn_256x128_e2048_fp16.onnx` (81 MB) is exempted: it carries no
biometric data and no customer weights, so it can be published, and the server
then needs nothing copied out of band. Every other model stays ignored and stays
on the server untouched.

If the model is somehow missing, the ReID path disables itself with a clear log
line and the rest of the service runs exactly as before - a data-collection
feature must never stop attendance from starting.

## Before anything: three things that decide whether this is safe

### 1. Does the server's gallery match its recognizer?

`load_gallery()` now **refuses to start** on a gallery built by a different
recognizer, because comparing one model's vectors against another's succeeds
silently and returns plausible-looking nonsense. That is the right behaviour, and
it means a mismatch takes the service down rather than quietly mis-attributing
attendance. **Check before restarting, not after.**

```bash
cd ~/faceid/ematsy
sqlite3 data/ematsy.db "select distinct model_name, count(*) from face_embedding group by 1;"
grep -E '^recognizer_model' .env || echo "(default: adaface_ir101_finetune_fp16.onnx)"
```

Expected: one row naming an `adaface_ir101_finetune` variant. The `_fp16` suffix
and `.enc` are ignored in the comparison, so `adaface_ir101_finetune.onnx` and
`adaface_ir101_finetune_fp16.onnx` are treated as the same model — deliberately,
because they differ by 0.0012 d′.

**If it names anything else, stop and say so.** The fix is `python scripts/enroll.py`,
which takes ~15 s but rebuilds the whole gallery.

### 2. The recognition threshold rises: 0.18 → 0.215

Calibrated on native-4K corridor footage: the worst impostor observed there
scores **0.195**, so 0.18 was *below* it — the system could and did name the
wrong person. 0.215 sits above every impostor measured, and keeps 87% of genuine
frames.

**Recognition rate will fall.** That is the intended trade: a miss costs nothing
because the person is seen again next pass, while a false accept writes one
person's name onto another's attendance and nothing in the data reveals it.

### 3. The live console's WebSocket URLs changed

`camera_stream.js` built its socket URLs against the bare host, so under
`/faceid` they resolved to the domain root - the camera feed and the attendance
push both 404'd while the page rendered fine. The page now passes the prefix
through `data-url-prefix`.

After Step 8, open the live console and confirm the camera tiles go **online**,
not just that the page loads. In the browser console there should be no
`WebSocket connection to 'wss://aiscan.airi.uz/ws/...' failed` - the URL must
contain `/faceid/ws/`.

### 4. `replay_dir` must not be set on the server

It makes workers read recordings instead of cameras. It is unset by default;
confirm nothing put it in `.env`:

```bash
grep -n replay ~/faceid/ematsy/.env || echo "  clean"
```

## Deploy

Run in the iClaude terminal on gpu6. Stop at the first step that does not do
what it says.

### Step 1 — back up the database

It is WAL, so `cp` can tear it. Use the backup API.

```bash
cd ~/faceid/ematsy
sqlite3 data/ematsy.db ".backup data/ematsy.pre-deploy-$(date +%Y%m%d_%H%M).db"
sqlite3 "data/ematsy.pre-deploy-$(date +%Y%m%d_%H%M).db" "pragma integrity_check;"
ls -la data/*.db
```

### Step 2 — stop the service, and PROVE it stopped

`SIGTERM` is not always enough: a worker blocked on an RTSP read can ignore it,
and it happened again during this work. If the restart proceeds anyway you get
**two processes on the same cameras and the same database** — the second binds
the port and looks healthy while the first keeps running the old code.

Never `pkill -f "scripts/run.py"` over SSH: the pattern matches the remote
shell's own command string and kills the session.

```bash
PID=$(ps -eo pid,cmd | awk '/faceid\/venv\/bin\/python/ && !/awk/ {print $1; exit}')
echo "stopping $PID"
kill "$PID"
for i in $(seq 1 25); do sleep 1; kill -0 "$PID" 2>/dev/null || break; done
kill -0 "$PID" 2>/dev/null && { echo "ignored SIGTERM, forcing"; kill -9 "$PID"; }
sleep 2
ps -eo pid,cmd | grep '[f]aceid/venv' || echo "  stopped"
ss -ltn | grep 8021 || echo "  port 8021 free"
```

### Step 3 — get the code

**If Step 0 said it IS a git checkout:**

```bash
cd ~/faceid/ematsy
git status --short          # .env, data/ and the .enc models are gitignored
git log --oneline -1        # note this: it is the rollback target
git remote -v || git remote add origin https://github.com/RamatovInomjon/attendance.git
git pull origin master
git log --oneline -3
```

**If it is NOT a git checkout** - clone beside it and carry the runtime state
over. `.env`, `data/` and the encrypted models are all gitignored, so a clone
has none of them and they must be moved deliberately:

```bash
cd ~/faceid
git clone https://github.com/RamatovInomjon/attendance.git ematsy-new
cp    ematsy/.env                 ematsy-new/
cp    ematsy/licence.key          ematsy-new/     2>/dev/null
mkdir -p ematsy-new/data ematsy-new/media
cp -a  ematsy/data/ematsy.db*     ematsy-new/data/
cp -a  ematsy/media/.             ematsy-new/media/   2>/dev/null
cp -a  ematsy/models/*.enc        ematsy-new/models/  2>/dev/null
ls ematsy-new/models/            # the .enc models plus reid_*.onnx from git
```

Keep the old directory until the new one has served real traffic; the rollback
is then a rename.

Then **delete the stale bytecode** — the compiled modules were replaced and a
cached `__pycache__` can shadow them:

```bash
rm -rf app/core/__pycache__ app/__pycache__ app/*/__pycache__
```

### Step 5 — schema and indexes

Additive only: two indexes added, three redundant ones dropped.

```bash
~/faceid/venv/bin/python scripts/migrate.py
```

### Step 6 — repair the damaged attendance rows

Three fixed bugs left damage that new code cannot correct on its own. **Dry run
first** — it prints every proposed change and writes nothing:

```bash
~/faceid/venv/bin/python scripts/migrate.py --skip-schema --repair-attendance
```

Read the output. It should show `NO_CHECKIN -> PRESENT` for rows that have a
check-in time, `presence INSIDE` on finished days, and cleared snapshot paths.
Then, if it looks right:

```bash
~/faceid/venv/bin/python scripts/migrate.py --skip-schema --repair-attendance --apply
```

### Step 7 — start, exactly one process

```bash
cd ~/faceid/ematsy
setsid nohup ~/faceid/start.sh > ~/faceid/run.log 2>&1 < /dev/null &
sleep 25
ps -eo pid,etime,cmd | grep '[f]aceid/venv'      # exactly ONE line
ss -ltnp | grep 8021
grep -E "recognizer|gallery|worker started|providers|ERROR" ~/faceid/run.log | head -12
```

Expect:

```
onnxruntime providers: ['TensorrtExecutionProvider', 'CUDAExecutionProvider']
gallery: <N> embeddings / <M> people
recognizer adaface_ir101_finetune_fp16.onnx: threshold=0.215
[Entrance] worker started (role=IN)
[Exit] worker started (role=OUT)
```

**`CUDAExecutionProvider` missing means it is running ~10x slower on CPU.** That
regression comes from `onnxruntime` (CPU) shadowing `onnxruntime-gpu`; it
happened again on the laptop during this work. Fix:
`~/faceid/venv/bin/pip uninstall -y onnxruntime && ~/faceid/venv/bin/pip install --force-reinstall --no-deps onnxruntime-gpu==1.23.2`
— uninstalling alone breaks both, because they share package files.

### Step 7b — confirm ReID came up

```bash
grep -E "reid" ~/faceid/run.log | head -4
```

Expect:

```
loaded reid_resnet101_ibn_256x128_e2048_fp16.onnx from vault (85.0 MB, ...)
reid ...: 256x128 embed=2048 CUDAExecutionProvider
reid worker started (..., 2048-d)
```

`reid: ... not found` or a decryption error means Step 3b did not land - the
service still runs, it just collects nothing. Body crops appear under
`data/persons/known|unknown/<date>/`; `/api/health` reports queue depth, crops
seen, crops dropped and matches under `reid`.

**Watch `crops_dropped`.** It should stay at 0. A rising count means the ReID
thread cannot keep up and is shedding work - which is the designed behaviour, not
a failure, but it means the collection is thinner than intended.

### Step 8 — check it in a browser, not curl

curl passed on both prefix bugs this deployment has already had. Open
`https://aiscan.airi.uz/faceid/` and confirm the dashboard renders, snapshots
load, and the live console shows both cameras.

```bash
curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1:8021/faceid/login
```

### Step 9 — watch one real pass

```bash
tail -f ~/faceid/run.log | grep -E "CHECK_IN|CHECK_OUT|DUPLICATE_VIEW|MISS"
```

`DUPLICATE_VIEW` is expected and is the point: it is the second camera's view of
one walk, recorded but not moving attendance state.

## Rollback

Code only, so it is a checkout and a restart. The database changes are additive
(indexes) plus the repair, which has its own backup from Step 1.

```bash
cd ~/faceid/ematsy
git checkout <the commit noted in Step 3>
rm -rf app/core/__pycache__ app/*/__pycache__
# stop and start per Steps 2 and 7
```

To roll back the repair as well, restore the Step 1 backup over `data/ematsy.db`
with the service stopped.

## What changes in behaviour

| | before | after |
|---|---|---|
| threshold | 0.18 (below the worst observed impostor) | **0.215** |
| one walk seen by both cameras | two contradictory transitions | one, from the stronger view |
| `NO_CHECKIN` after a later check-in | stayed flagged forever | clears |
| step out and return within 90 s | return silently dropped | recorded |
| end-of-day sweep | never ran (timer not installed) | runs in-process, all unfinished days |
| camera dropout | old tracks re-attach to new people | tracks closed, tracker reset |
| reader thread crash | thread dies, camera gone until restart | reconnects |
| `/video/<id>` viewer | blocks the event loop | off-thread |
| gallery from another recognizer | silently wrong matching | refused at startup |
| an unrecognised pass on the dashboard | 112x112 aligned face | body crop |
| body crops / ReID | did not exist | collected, matched Entrance->Exit |
| gallery | enrolment photos only | admin can add corridor crops at /gallery/review |

Unchanged and worth knowing: `debug_capture` is still on by default, so each
recognised pass still writes four files plus a JSON to `data/debug/`. Set
`debug_capture=0` in `.env` if that disk churn is unwanted — it costs the
forensic images that have been useful for explaining wrong matches.

## What the ReID addition costs on the server

| | |
|---|---|
| GPU | one more session, ~85 MB weights. The RTX 3090 has 24 GB. |
| CPU | one extra thread; JPEG encode plus 1.4 ms/crop of inference. |
| disk | ~10 crops per pass at ~40 KB. At ~300 passes/day, **~120 MB/day**. |
| retention | `reid_retention_days = 30` -> ~3.5 GB steady state, swept by the in-process end-of-day job. gpu6 has 812 GB free. |
| database | one new table, `reid_pass`, one row per pass. |

It writes no attendance and cannot: `AttendanceService` is never called from the
ReID path. On its own cross-camera test set the model misses ~31% of genuine
queries at a 10% false-positive rate, which is useful for collecting training
data and nowhere near good enough to name somebody.

**Body crops of unidentified people are biometric data.** They live under
`data/persons/`, deliberately outside the public `media/` mount, and expire on
the retention above. `face_id_users/README` already flags this class of data as
needing restricted access; the same applies here.
